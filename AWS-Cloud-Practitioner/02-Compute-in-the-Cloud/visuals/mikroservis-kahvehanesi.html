Denemek için: SQS modunda baristayı çökert, birkaç sipariş ver, sonra baristayı geri getir. Hiçbir sipariş kaybolmaz; kuyruk birikir, sonra erir. Aynı şeyi "direkt çağrı" modunda yap: kasiyer ayakta olsa bile siparişler hata verir. Buna tightly coupled denir.

"Mikroservis yazmak" pratikte ne demek?

Bir mikroservis, tek bir iş yeteneğini üstlenen, kendi başına deploy edilen küçük bir uygulamadır. Kod yazma şeklin çok değişmez: yine bir Express, FastAPI ya da Spring uygulaması yazarsın. Değişen şey sınırlardır. Modüller aynı process içinde fonksiyon çağırmak yerine ağ üzerinden, sözleşmeyle konuşur.

Kendi verisiHer servisin kendi veritabanı var. Başka servisin tablosuna doğrudan dokunmaz, onun API'sini ya da mesajını kullanır.

Nasıl görünür: kod

AWS SDK for JavaScript (v3) ile üç servisin iletişim kısmı. İş mantığı sıradan kod; mikroservisi mikroservis yapan, aradaki bu birkaç satır.

order-service · kuyruğa yaz

import { SQSClient, SendMessageCommand } from "@aws-sdk/client-sqs";
const sqs = new SQSClient({});

app.post("/orders", async (req, res) => {
  const order = { id: crypto.randomUUID(), ...req.body };
  // Baristayı çağırmaz; siparişi panoya asar.
  await sqs.send(new SendMessageCommand({
    QueueUrl: process.env.ORDERS_QUEUE_URL,
    MessageBody: JSON.stringify(order),  // payload
  }));
  res.status(202).json({ id: order.id }); // "alındı"
});

barista-service · kuyruktan oku

while (true) {
  const { Messages } = await sqs.send(new ReceiveMessageCommand({
    QueueUrl, MaxNumberOfMessages: 10,
    WaitTimeSeconds: 20,  // long polling
  }));
  for (const m of Messages ?? []) {
    await makeDrink(JSON.parse(m.Body!));
    // İş bitince sil; bitmezse mesaj kuyrukta kalır.
    await sqs.send(new DeleteMessageCommand({
      QueueUrl, ReceiptHandle: m.ReceiptHandle! }));
    await sns.send(new PublishCommand({
      TopicArn: DRINK_READY_TOPIC, Message: m.Body! }));
  }
}

Son satırdaki PublishCommand SNS'e tek bir mesaj yollar. SNS onu topic'e abone olan herkese dağıtır (fan-out): e-posta, SMS, mobil push ya da başka bir servis. Barista, bildirimi kimin aldığını bilmez.

Bedeli: mikroservis bedava değil

Kurs, mikroservisin avantajlarını anlatıyor. Gerçek hayatta bir de fatura ve operasyon yükü var:

  • Ağ hatası yeni bir hata türü. Fonksiyon çağrısı neredeyse hiç başarısız olmaz; ağ çağrısı olur. Retry, timeout ve aynı mesajın iki kez işlenmesi (idempotency) senin sorunun olur.
  • Tutarlılık gecikir. Sipariş "alındı" dendiği anda içecek henüz yok. Buna eventual consistency denir; arayüzün bunu göstermesi gerekir.
  • Hata ayıklama zorlaşır. Bir istek dört servisten geçiyorsa, tek bir log dosyası yetmez. Dağıtık izleme (tracing) gerekir.
  • Maliyet ve iş yükü artar. Her servis için ayrı deploy, izleme ve sürekli çalışan kaynak. Küçük bir ekip için bu, kazandığından fazlasını alabilir.

Pratik öneri: Tek geliştirici ya da küçük ekip için en iyi başlangıç genelde modüler monolittir: tek deploy, ama modüller arasında net sınırlar. Bir modülün ölçeklenme ihtiyacı ya da ekibi gerçekten ayrışınca onu servise çıkarırsın. Önce ayrılan parça genelde kuyruğun arkasındaki yavaş iş olur, bu simülatördeki barista gibi.
